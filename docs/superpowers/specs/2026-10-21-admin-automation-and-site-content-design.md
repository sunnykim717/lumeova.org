# 관리자 업무 자동화 및 공개 사이트 내용 갱신 설계

- 상태: **초안 — 사용자 승인 대기** (승인 전 구현하지 않음)
- 작성일: 2026-10-21
- 범위: 설계 문서만 작성. 구현 코드, 마이그레이션 실행, 배포 변경 없음.
- 작업 순서: (1) 관리자 업무 감소 → (2) 공개 사이트 내용 주기적 갱신

---

## 0. 요약

1. **입금 대조 보조**: 은행 거래내역 CSV를 올리면 기존 후원 신청과 대조해 "확인 추천 / 검토 필요" 후보를 보여준다. 관리자가 선택하고 버튼을 눌러야 입금 확인이 된다. 자동 확정은 없다.
2. **회원 승인 보조**: 승인 대기 목록에 자동 점검 항목(필수값, 중복 의심, 이미 승인된 동일인)을 표시한다. 일괄 승인은 "모든 점검 통과 + 일반회원"으로 좁히고, 확인 다이얼로그를 거친다.
3. **소식·사업 등록 템플릿**: 유형별 본문 틀, 슬러그 제안, 발행 전 체크리스트(사진 동의 포함).
4. **외부 시트 → 소식 반영**: 정해진 주기(기본 하루 1회)로 시트 CSV를 읽어 `news`에 반영한다. 시트에 적힌 `status`가 게시 승인 역할을 하며, 관리자가 UI에서 고친 행은 시트가 덮어쓰지 않는다.
5. **집계 통계**: 승인 회원 수, 누적 확정 후원액 등 **집계값만** `site_stats` 테이블에 두고 공개 사이트는 그 테이블만 읽는다. 개별 회원·후원자 데이터에는 공개 경로가 생기지 않는다. 수혜자 수 같은 값은 DB에서 계산하지 않고 단체가 직접 제공한 값만 쓴다.

## 1. 목적

- 관리자(`/admin`)가 매번 손으로 옮기는 작업(입금 대조, 승인 전 확인, 소식 등록)을 줄인다.
- 사이트의 "준비중" 자리(소식, 통계)가 사람의 반복 작업 없이 최신 상태를 유지하도록 한다.
- 돈과 개인정보에 관한 결정권은 계속 사람에게 둔다.

## 3. 목표와 비목표

### 3.1 공통 원칙

- **G0-1** 돈과 관련된 확정(입금 확인, 후원 상태 변경, 정회원 승인, 금액 수정)은 자동으로 실행하지 않는다. 항상 관리자 세션 + 버튼 클릭이다.
- **G0-2** 공개 사이트는 개인 식별 정보와 개별 후원자 정보를 노출하지 않는다. 공개 가능한 것은 집계값과 게시된 소식뿐이다.
- **G0-3** 권한 경계는 Postgres RLS다. 페이지 가드와 UI 숨김은 편의 기능이다. 새 기능은 모두 RLS 정책을 함께 추가한다.
- **G0-4** 서비스 롤 키는 원칙적으로 쓰지 않는다. 쓰려면 결정 사항(§8.13)으로 승인을 받는다.

### 3.2 1번 — 관리자 업무 감소

- **목표**
  - 은행 거래내역 CSV와 신청 목록의 대조를 후보 제시까지 자동화하고, 최종 확인은 사람이 한다.
  - 승인 대기 회원에 대해 점검 항목을 자동 표시하고, 조건이 명확한 경우만 일괄 승인을 허용한다.
  - 소식·사업 등록 시 틀과 발행 전 체크리스트를 제공한다.
- **비목표**
  - 입금 자동 확정, 자동 승인, 자동 반려.
  - 분할 입금·합산 입금(한 번에 여러 후원을 낸 경우)의 자동 매칭. 이 경우는 "검토 필요"로만 표시한다.
  - 은행 API 연동(오픈뱅킹 등). CSV 업로드만 다룬다.
  - 입금 대조 결과 저장을 위한 별도 알림 기능(이메일·푸시).
  - AI 기반 문안 생성, 자동 번역.

### 3.3 2번 — 사이트 내용 주기적 갱신

- **목표**
  - 외부 시트의 소식을 정해진 주기로 `news`에 반영한다. 시트를 고친 사람이 게시 승인자가 된다.
  - 집계 통계로 통계 자리를 채우되, 최소 표시 기준 미만이면 "준비중"을 유지한다.
- **비목표**
  - 시트를 편집 원본으로 삼는 양방향 동기화. 시트 → DB 단방향만 한다.
  - 사업(`projects`)의 시트 연동. 1차는 소식만 다룬다. 사업은 등록 템플릿(1번)만 적용한다.
  - 수혜자 수, 연혁, 협력기관, 해외 국가 목록 등을 DB에서 계산해 채우는 것. 이 값들은 단체가 제공한 확인된 값만 쓴다(README "Never fabricate org facts").
  - 공개 통계 차트·세부 분석 페이지.
  - 실시간 갱신. 주기 갱신과 관리자 수동 "지금 갱신"만 둔다.

## 4. 제약

- **C1 DB 상태**: Supabase 실제 프로젝트에 `0001`이 아직 실행되지 않았다. `0002`도 같은 방식으로 검토 후 실행한다. 새 Supabase 프로젝트를 만들지 않는다(`0001` 주석의 프로젝트 규칙).
- **C2 실행 환경**: Next.js 16 + OpenNext(Cloudflare). 서버 전용 코드는 `server-only`를 쓴다. 현재 `wrangler.jsonc`에는 R2도, cron도 없다. ISR 캐시도 아직 없어서 통계 페이지는 요청 시점에 읽는다고 가정하고, 구현 단계에서 확인한다.
- **C3 레이트리밋**: `src/lib/utils/rateLimit.ts`는 인스턴스 메모리 기반이라 업로드·동기화 엔드포인트를 보호하기에 부족하다. 동기화는 공유 비밀값으로 보호하고, 업로드는 관리자 세션으로만 허용한다.
- **C4 입금 CSV 형식**: 샘플이 없다. 신한은행 인터넷뱅킹 CSV는 인코딩(UTF-8 또는 CP949/EUC-KR)과 열 이름이 다를 수 있다. 샘플을 받기 전까지 파서는 열 이름 매핑 설정으로 분리하고, 실제 샘플로만 검증한다.
- **C5 개인정보**: 은행 거래내역에는 상대방 이름과 계좌 정보가 있다. 필요한 열만 저장하고 원본 파일은 저장하지 않는다(§5.1.4).
- **C6 개인정보처리방침 초안**: `PRIVACY_POLICY_VERSION = "2026-09-draft"`, 보유 기간과 제3자 제공 문구가 미확정이다. 은행 거래내역 처리, 시트 연동, 집계 공개 목적을 확정 전에 반영해야 한다.
- **C7 공개 시트**: "웹에 게시"한 CSV는 누구나 읽을 수 있다. 소식 내용만 두고, 개인정보는 시트에 적지 않는 규칙을 둔다.
- **C8 법적 상태**: 단체는 "비영리 임의단체"다(`brand.ts`). 누적 후원액을 공개하는 것이 적절한지 대표자 확인이 필요하다(§8.8).

## 5. 설계 — 1번: 관리자 업무 감소

### 5.1 입금 대조 보조

#### 5.1.1 흐름

1. 관리자가 `/admin/donations/import`에서 은행 거래내역 CSV를 올린다. 업로드는 관리자 세션을 확인한 서버 액션이나 Route Handler에서 처리한다.
2. 서버가 인코딩을 판별하고(UTF-8 우선, 실패하면 EUC-KR), 열 매핑 설정에 따라 파싱한다. **입금 행만** 남긴다(입금액 > 0, 출금 행 제외).
3. 각 행을 `bank_transactions`에 저장한다. 같은 거래는 중복 저장하지 않는다.
4. 후보 계산은 **조회 시점에 서버에서** 한다. 결과를 저장하지 않으므로 신청 상태가 바뀌면 바로 반영된다.
5. 관리자가 행을 골라 "선택 항목 입금 확인"을 누른다. 확인 요약(건수, 합계, 이름, 날짜)을 보여준 뒤 한 번 더 확인받는다.
6. 확정은 Postgres 함수 `confirm_donation_payments(...)`가 한 트랜잭션으로 처리한다. 금액과 날짜는 클라이언트가 보낸 값이 아니라 `bank_transactions` 값을 쓴다.

#### 5.1.2 후보 분류 규칙

거래 한 건(T)과 미확인 후원 신청(D)을 비교한다. "미확인"은 상태가 `active`이고 `confirmed` 행이 없는 신청이다.

| 등급 | 조건 | 화면 표시 | 기본 선택 |
|---|---|---|---|
| **확인 추천** | 금액 정확 일치 **그리고** 이름 정규화 일치 **그리고** T의 날짜가 D의 `created_at`부터 +30일 이내 **그리고** 같은 금액·이름의 미확인 신청이 D 하나뿐 | 초록 배지 | 선택 가능, 기본 미선택 |
| **검토 필요** | 금액만 일치, 이름만 일치, 같은 조건의 신청이 여러 건, 또는 날짜 범위 밖 | 노랑 배지, 후보를 모두 나열 | 선택 불가. 관리자가 후보를 고른 뒤 확인 |
| **매칭 없음** | 위 조건에 맞는 신청이 없음 | 회색 | 확인 불가 |

- 이름 정규화: 앞뒤 공백 제거, 내부 공백 제거, 괄호 내용 제거, 전각→반각. 한글 이름은 완전 일치만 본다. 유사도 매칭은 하지 않는다(오확정 위험).
- 은행 적요(메모)와 보낸분 이름이 다를 수 있다. 적요에 신청자 이름이 있으면 보조 점수로만 쓰고, 등급을 올리는 근거로는 쓰지 않는다.
- 한 거래가 두 후원의 합계일 가능성은 계산하지 않는다. 금액이 어떤 신청과도 맞지 않으면 "매칭 없음"으로 둔다.

#### 5.1.3 DB 가드레일 (`0002` 초안)

```text
bank_transactions
  id                 uuid pk
  transacted_at      timestamptz not null        -- 거래 일시
  amount             integer not null check (amount > 0)
  counterparty_name  text                        -- 보낸분 (입금자명)
  memo               text                        -- 적요
  dedupe_key         text not null unique        -- sha256(거래일시|금액|보낸분|적요|은행 거래번호 있으면 포함)
  matched_payment_id uuid unique references donation_payments (id)
  imported_by        uuid references admin_users (id)
  imported_at        timestamptz not null default now()
  -- 잔액, 계좌번호, 원본 CSV는 저장하지 않는다.
```

- `donation_payments`에 **부분 유니크 인덱스** 추가: `unique (donation_id) where status = 'confirmed'`. 한 후원에 확정 행은 하나만 생긴다. 분할 입금 허용 여부는 §8.2에서 결정한다.
- `bank_transactions.matched_payment_id`는 유니크다. 한 입금이 두 확정에 쓰일 수 없다.
- RLS: `bank_transactions`는 `is_admin()`만 읽기·쓰기. anon, 일반 supporter는 접근할 수 없다.
- `confirm_donation_payments`는 `security invoker`로 만든다. 함수 안에서 `is_admin()`을 먼저 검사하고, 기존 `donation_payments` RLS가 그대로 적용된다. 실패하면 전체를 롤백한다.

#### 5.1.4 개인정보 최소화

- 저장하는 열: 거래 일시, 입금액, 보낸분, 적요, 중복 키, 확정 연결, 가져온 관리자, 가져온 시각.
- 저장하지 않는 열: 잔액, 계좌번호, 은행 내부 거래번호(없으면 dedupe에만 사용), 원본 파일.
- 원본 CSV는 메모리에서만 파싱하고 버린다.
- 보유 기간: 기본 안을 1년으로 둔다. 확정 여부와 무관하게 기간이 지나면 삭제하는 작업이 필요하다. 최종 기간은 §8.4에서 결정한다.

#### 5.1.5 관리자 화면

- `/admin/donations/import`: 파일 선택, 열 매핑 설정 확인, 파싱 결과 요약(입금 n건, 중복 n건 제외, 파싱 실패 n건).
- 결과 탭: "확인 추천 / 검토 필요 / 매칭 없음".
- 기존 `/admin/donations`의 "입금확인" 버튼은 그대로 둔다. 파일 없이 수동으로 확인하는 경로다. 다만 금액 입력이 신청 금액과 다르면 경고를 보이고 사유 메모를 요구한다(§8.3).
- 대시보드의 "입금 미확인 후원" 카드 링크가 동작하도록 `?filter=unconfirmed`를 후원 목록에 실제로 연결한다. 기존 결함이므로 이 작업에 포함한다.

#### 5.1.6 감사 로그

- `audit_logs`에 확정 한 건마다 기록한다. `metadata`에 `bank_transaction_id`, 매칭 등급, 금액 일치 여부를 담는다.
- `logAction`이 `metadata`를 받을 수 있도록 시그니처를 확장한다(현재는 저장하지 않음).

### 5.2 회원 승인 보조

#### 5.2.1 점검 항목 (표시만 함)

점검 결과는 `src/lib/validation/` 옆의 상수 모듈에 정의한 규칙으로 계산한다. 규칙은 코드로 버전 관리하고 바꿀 때 기록을 남긴다.

| 코드 | 점검 | 기준 |
|---|---|---|
| `REQUIRED_OK` | 필수값 완비 | 이름 있음, 연락처 또는 이메일 중 하나 있음, 개인정보 동의 행 있음 |
| `DUP_SUSPECT` | 중복 의심 | 정규화한 전화번호 또는 이메일이 다른 `supporters`와 같음 |
| `ALREADY_APPROVED` | 이미 승인된 회원 | 같은 사람(중복 의심 대상)에게 `approved` 멤버십이 이미 있음 |
| `BIRTH_MISSING` | 생년월일 누락 | 정회원 신청이면서 `birth_date`가 없음(정회원 요건 확인 후 적용, §8.5) |

- 전화번호 정규화: 숫자만 남기고 `010`으로 시작하는지 확인한다.
- 중복 의심은 **차단하지 않는다.** 가족이 같은 번호를 쓰는 경우가 있으므로 관리자가 판단한다.

#### 5.2.2 일괄 승인 범위

- 대상: "`REQUIRED_OK`이고 `DUP_SUSPECT`와 `ALREADY_APPROVED`가 아니며 **일반회원**(`general`)인 행".
- 정회원(`regular`)은 자동 승인 대상이 아니다. 기존 주석("the system never auto-approves regular membership, per spec §11")을 그대로 따른다. 정회원은 행마다 사람이 승인한다.
- 흐름: 대상 행 체크 → 요약 다이얼로그(건수와 이름 목록) → 확인 → 승인. 실행은 기존 `updateMembershipStatus`를 재사용하고, 행마다 감사 로그를 남긴다.
- 실패한 행은 건너뛰고 결과 목록에 표시한다.

#### 5.2.3 데이터 변경

- 스키마 변경 없음. 점검 결과는 계산해서 보여준다.
- 거절 사유 템플릿은 1차에서 제외한다(§8.5에서 필요성 확인).

### 5.3 소식·사업 등록 템플릿

#### 5.3.1 기능

- **본문 틀**: 등록 화면에서 유형을 고른다. 활동 보고, 사업 소개, 공지 세 가지 틀을 제공하고, 헤딩과 빈 문단을 채운다. 내용은 관리자가 직접 쓴다.
- **슬러그 제안**: 제목에서 영문·숫자만 남긴 값이 비면 `YYYY-MM-DD-` 접두어와 입력칸을 제공한다. 기존 패턴 `[a-z0-9-]+`는 그대로 유지한다.
- **발행 전 체크리스트**: 게시 상태(`published`)로 저장하려면 아래 항목을 확인한다.

| 항목 | 종류 | 설명 |
|---|---|---|
| 사진·실명 동의 | **필수** | 사람 사진이나 수혜자 식별 정보가 있으면 동의 체크를 해야 게시된다 |
| 썸네일 | 경고 | 없으면 플레이스홀더가 나온다는 점을 알린다(README: 사진은 실제 사진이 있을 때만) |
| 준비중·TODO 문자열 | 경고 | 본문에 "준비중", "TODO"가 있으면 알린다 |
| 게시일 | 경고 | 미래 날짜면 예약처럼 보이므로 알린다 |

- 체크 결과는 저장 차단이 아니라 **필수 항목만 차단**한다. 나머지는 경고다.

#### 5.3.2 데이터 변경

- 필수 체크를 기록하려면 `news`, `projects`에 `consent_confirmed_at timestamptz null`을 추가한다(`0002`). 필요 여부는 §8.14에서 확인한다.

## 6. 설계 — 2번: 사이트 내용 주기적 갱신

### 6.1 외부 시트에서 소식 반영

#### 6.1.1 소스와 열 규약 (v1)

- 소스: Google 스프레드시트의 "웹에 게시" CSV URL 하나. URL은 **환경 변수** `NEWS_SHEET_CSV_URL`에만 둔다. 요청이나 화면에서 받는 URL은 허용하지 않는다(SSRF 방지).
- 가져올 때 시간 제한(예: 10초)과 크기 제한(예: 1MB, 행 500개)을 둔다.

| 열 | 필수 | 규칙 |
|---|---|---|
| `external_id` | 예 | 고유값. 한 번 정하면 바꾸지 않는다. 없는 행은 건너뛴다 |
| `title` | 예 | 1~200자 |
| `slug` | 아니오 | 없으면 `external_id`를 소문자 영숫자·하이픈으로 바꿔 쓴다 |
| `category` | 아니오 | 텍스트 |
| `summary` | 아니오 | 목록 노출용, 200자 이내 |
| `content` | 아니오 | 본문, 5만 자 이내. HTML은 허용하지 않고 텍스트로 저장 |
| `published_at` | 아니오 | `YYYY-MM-DD` |
| `status` | 아니오 | `draft` \| `published` \| `hidden`. 비우면 `draft` |
| `thumbnail` | 아니오 | `/`로 시작하는 `public` 하위 경로만. 외부 URL 금지 |

- 개인정보 열(전화번호, 이메일 등)이 있으면 동기화를 중단하고 오류를 기록한다.

#### 6.1.2 DB 변경 (`0002`)

```text
news
  + external_id      text unique            -- 시트 행 식별자, 수동 등록 행은 null
  + source           text not null default 'manual' check (source in ('manual','sheet'))
  + source_synced_at timestamptz
  + admin_locked     boolean not null default false
```

- `sync_runs` 테이블을 추가해 실행 시각, 결과(추가 n, 갱신 n, 건너뜀 n, 오류 목록), 소스 해시를 남긴다. RLS는 관리자 읽기 전용.

#### 6.1.3 반영 규칙

| 상황 | 처리 |
|---|---|
| 새 `external_id` | `source='sheet'`, `admin_locked=false`로 **추가**. 시트의 `status` 값을 그대로 쓴다 |
| 기존 `sheet` 행, `admin_locked=false`, 값이 바뀜 | 시트 값으로 **갱신**. `source_synced_at` 갱신 |
| 기존 `sheet` 행, `admin_locked=true` | **갱신하지 않는다.** 결과에 "관리자 수정 우선"으로 기록하고 관리자 목록에 표시 |
| 시트에서 행이 사라짐 | **삭제하지도 숨기지도 않는다.** 결과에만 기록한다(§8.11) |
| `manual` 행과 같은 `slug` | 충돌로 기록하고 건너뛴다. 덮어쓰지 않는다 |

- 관리자가 `/admin/news/[id]/edit`에서 `sheet` 행을 저장하면 `admin_locked=true`로 바꾼다. 관리자가 잠금을 풀 수 있는 버튼도 둔다.
- **게시 승인은 시트의 `status`다.** 시트 편집자가 `published`로 적으면 다음 주기에 공개된다. 이것이 1번의 "검토" 역할을 대신하므로 관리자 작업이 줄어든다. 자동 게시를 끄고 모든 신규 행을 `draft`로 만드는 방식도 가능하다(§8.10).

#### 6.1.4 실행 방식

- 트리거: 하루 1회(기본 안, 시각은 §8.12). 관리자는 "지금 동기화"를 누를 수 있다.
- 엔드포인트: `POST /api/cron/sync-news`. `Authorization: Bearer <CRON_SECRET>`를 **상수 시간 비교**로 확인한다. 실패하면 401.
- 호출 주체 후보:
  - **A. GitHub Actions 스케줄** (권장): 배포 방식과 무관하게 동작하고, 실행 로그가 남는다. `CRON_SECRET`은 GitHub Secrets와 서버 환경 변수 두 곳에 둔다.
  - B. Cloudflare Cron Trigger: OpenNext 워커 진입점에 `scheduled` 핸들러를 추가해야 한다. 첫 배포 후 검토한다.
  - C. Supabase `pg_cron` + `pg_net`: DB에 비밀값을 넣어야 하므로 권장하지 않는다.

#### 6.1.5 쓰기 권한 (결정 필요)

동기화는 관리자 세션 없이 실행되므로 RLS를 통과할 주체가 없다. 선택지는 두 가지다.

- **안 1 (권장, §8.13 승인 필요)**: 서비스 롤 키를 서버 환경 변수로만 두고, `createAdminClient()`를 **동기화 모듈 한 곳에서만**쓴다. 이 모듈은 `source='sheet'` 행만 쓰도록 코드로 제한하고, 테스트로 확인한다. 기존 `.env.example`과 README의 "서비스 롤 키 불필요" 문구는 이 결정에 맞춰 고친다.
- 안 2: 서비스 롤 없이 `SECURITY DEFINER` 함수 `sync_news_rows(jsonb)`를 만들고, 호출자를 비밀값으로 확인한다. 비밀값을 DB 안에 두어야 하므로 구조가 복잡하고 실수 여지가 많다.

### 6.2 집계 통계로 "준비중" 자리 채우기

#### 6.2.1 지표 후보와 제외 항목

| 지표 | 계산 기준 | 상태 |
|---|---|---|
| 승인된 회원 수 | `memberships.status = 'approved'`의 `supporter_id` 고유 개수 | 후보 (§8.6에서 정회원만 또는 전체 중 결정) |
| 누적 확정 후원액 | `donation_payments.status = 'confirmed'`의 `amount` 합계 | 후보 (신청액은 쓰지 않는다) |
| 후원에 참여한 사람 수 | `confirmed` 입금이 있는 `supporter_id` 고유 개수 | 후보, 최소 기준 적용 시에만 |
| 발행된 소식 수 | `news.status = 'published'` 개수 | 후보, 위험 낮음 |
| 수혜자 수 | **DB 계산 안 함** | 단체 제공값만. `brand.ts`의 `beneficiaryCount`는 수동 입력 |
| 연혁, 협력기관, 해외 국가 | **DB 계산 안 함** | 단체 제공값만 |

- **제외**: 지역·나이·성별 등 세부 분할(작은 집단이 되어 개인이 드러날 수 있음), 개인 이름, 미확인·신청 중 금액, 유형별 세부 금액.

#### 6.2.2 공개 경로

- 새 테이블 `site_stats`:

```text
site_stats
  key        text pk            -- 'approved_members', 'confirmed_total', ...
  value      numeric not null
  as_of      timestamptz not null
  visible    boolean not null default false
  -- 공개 값은 이 테이블에서만 읽는다
```

- RLS: `select` 정책은 `visible = true`인 행에 대해 **anon을 포함한 모두 허용**. `insert/update/delete`는 `is_admin()`만.
- 값은 `refresh_site_stats()` 함수가 계산한다. 이 함수는 `SECURITY DEFINER`이며 안에서 `is_admin()` 또는 서비스 롤 호출만 허용한다. anon은 실행할 수 없다. 결과에는 식별자가 없다.
- 공개 페이지는 `supporters`, `memberships`, `donations`를 직접 읽지 않는다. `site_stats`만 읽는다. 이 경계를 깨지 않는지 확인하는 검증 항목을 §7에 둔다.

#### 6.2.3 최소 표시 기준과 표시 형식

- 최소 기준 N (기본 안 10, §8.7): 집계 대상이 N 미만이면 `visible=false`로 두고 "준비중"을 그대로 보여준다.
- 누적 금액 표시: 기본 안은 **만원 단위 내림**과 "이상"이라는 말을 붙인다(예: "1,230만 원 이상"). 정확한 값을 공개할지는 §8.8에서 결정한다.
- 기준일: 모든 값 옆에 `as_of` 날짜를 표시한다.

#### 6.2.4 갱신 주기와 승인

- 주기: 하루 1회. 6.1.4와 같은 엔드포인트 또는 같은 워크플로에서 `refresh_site_stats()`를 호출한다.
- 관리자 "지금 갱신" 버튼과, 개별 지표를 숨기는 `visible` 토글을 `/admin/dashboard`에 둔다.
- 자동 공개 여부는 §8.9에서 결정한다. 기본 안은 **자동 공개 + 관리자가 언제든 숨길 수 있음**이다. 숫자는 확정된 입금에서만 파생되므로 자동 공개 위험이 낮다고 판단했다.

#### 6.2.5 프런트엔드

- 새 컴포넌트 `SiteStats`(홈과 소개 페이지에 배치)가 `getPublicStats()`로 읽는다. `src/lib/data/content.ts`의 fail-soft 패턴을 따른다. 설정이 없거나 오류면 빈 배열을 돌려주고, 컴포넌트는 "준비중" 자리를 그린다.
- 새 지표가 0개면 섹션 자체를 숨기지 않고 "준비중"을 보여준다(기존 빈 상태 문구와 맞춘다).

## 7. 검증 계획 (구현 단계)

- **파서**: 실제 신한은행 CSV 샘플(개인정보 마스킹본)로 인코딩, 열 매핑, 입금·출금 구분을 테스트한다. 샘플이 없으면 구현을 시작하지 않는다.
- **후보 분류**: 확인 추천, 검토 필요, 매칭 없음, 중복 거래, 동일 금액 복수 신청 각각의 단위 테스트.
- **DB**: `0002` 적용 후 SQL로 확인.
  - 같은 후원에 `confirmed` 두 건 삽입 → 실패해야 함.
  - 같은 `dedupe_key` 두 건 → 실패해야 함.
  - anon 키로 `supporters`, `memberships`, `donations`, `donation_payments`, `bank_transactions` 조회 → 0건 또는 거부.
  - anon 키로 `refresh_site_stats()` 호출 → 거부.
  - anon 키로 `site_stats`의 `visible=true` 행 조회 → 성공, `visible=false` → 0건.
- **동기화**: 열 규약 위반, 개인정보 열 포함, 잠긴 행, 같은 slug 충돌, 시트에서 행 삭제, 크기 초과 각각 테스트.
- **인증**: `CRON_SECRET` 없음·틀림 → 401. 업로드 엔드포인트 비관리자 → 403.
- **테스트 DB**: 기존 Supabase 프로젝트에 적용하기 전에 검증할 장소가 필요하다(§8.15). 로컬 Supabase CLI를 쓸 수 있으면 그곳에서 먼저 실행한다.

| 8.4 | 입금 거래 원본(이름·적요) 보유 기간은? | 1년 후 자동 삭제 | 개인정보처리방침 초안이 미확정이다 |
| 8.5 | 일괄 승인 대상은 일반회원만인가? 정회원 요건(생년월일 등)은 무엇인가? | 일반회원만, 정회원은 행별 승인 | 현재 주석과 spec §11 해석이 필요하다 |
| 8.6 | 공개 "회원 수"는 정회원만, 전체 중 무엇을 셀까? | 전체 승인 회원 | 단체 설명에 맞춰야 한다 |
| 8.7 | 집계 최소 표시 기준 N은? | 10 | 작은 수는 개인을 드러낼 수 있다 |
| 8.8 | 누적 후원액을 공개해도 되는가? 표시 단위는? | 공개, 만원 단위 내림 + "이상" | 비영리 임의단체의 공개 정책을 대표자가 확인해야 한다 |
| 8.9 | 집계 값은 자동 공개할까, 관리자 확인 후 공개할까? | 자동 공개 + 언제든 숨김 | 확정된 입금에서만 파생되므로 위험이 낮다 |
| 8.10 | 시트의 `status=published`를 게시 승인으로 볼까? | 예 (시트 편집자가 승인자) | 관리자 작업을 가장 많이 줄인다. 아니면 모든 신규 행을 `draft`로 만든다 |
| 8.11 | 시트에서 행을 지우면 DB에서는 어떻게 할까? | 아무것도 하지 않고 기록만 | 실수로 지운 행이 사라지는 것을 막는다 |
| 8.12 | 소식 동기화 주기와 실행 방식은? | 하루 1회, GitHub Actions | 배포 방식과 무관하게 동작한다 |
| 8.13 | 서비스 롤 키를 동기화 모듈 한 곳에서만 쓰는 예외를 승인하는가? | 승인 (안 1) | README의 "서비스 롤 키 불필요" 원칙의 예외다. 승인이 있어야 구현한다 |
| 8.14 | 사진·실명 게시 동의 체크를 필수로 할까? | 필수 | 수혜자 식별 정보가 공개되는 것을 막는다 |
| 8.15 | 검증용 DB는 어디에 둘까? (기존 프로젝트 안의 스테이징, 로컬 CLI 등) | 로컬 Supabase CLI | 프로젝트 규칙상 새 Supabase 프로젝트는 만들지 않는다 |
| 8.16 | 공개 소식 시트를 "웹 게시" CSV로 할까, 비공개 시트(서비스 계정)로 할까? | 웹 게시 CSV | 구현이 단순하다. 소식만 두는 것이 조건이다(C7) |

## 9. 구현 단위 (승인 후, 독립 PR 권장)

1. **1A** `0002` 마이그레이션(유니크 인덱스, `bank_transactions`, 확정 함수) + SQL 검증.
2. **1B** 입금 CSV 업로드, 파서, 후보 분류, 확정 화면. 파서 픽스처 테스트.
3. **1C** 회원 점검 항목 표시, 일반회원 일괄 승인.
4. **1D** 소식·사업 등록 틀, 슬러그 제안, 발행 전 체크리스트.
5. **2A** `news` 열 추가, 시트 동기화 모듈, `sync_runs`, `POST /api/cron/sync-news`, 워크플로 파일.
6. **2B** `site_stats`, `refresh_site_stats()`, 관리자 대시보드 토글.
7. **2C** `SiteStats` 컴포넌트와 `getPublicStats()`, 통계 자리 교체.

각 단계는 `0001`과 기존 공개 페이지를 깨지 않아야 하며, 단계마다 §7의 해당 검증을 통과해야 다음 단계로 간다.
